# פריסת מסך האישורים

## דרישה, לא המלצה

`npm run dashboard` **אינו מסיים TLS**. השרת מאזין על ממשק הלולאה החוזרת (`127.0.0.1`) בלבד ואסור לו להיקשר לממשק ציבורי ישירות — לא בהגדרת ברירת המחדל, ולא בשינוי ידני של `DASHBOARD_HOST`. גישה מהאינטרנט עוברת דרך מנהרה (tunnel) או reverse proxy שמסיים TLS מולה, ורק אחר כך מעביר את הבקשה, כטקסט רגיל, אל השרת המקומי.

זו לא המלצה שאפשר לדלג עליה מתוך נוחות. עוגיית הסשן נכתבת עם התכונה `Secure`, כלומר הדפדפן **לעולם לא ישלח אותה** מעל חיבור לא-מוצפן. פריסה שגויה — חשיפת הפורט הזה ישירות לאינטרנט בלי proxy מולו — אינה נכשלת בקול: היא פשוט **מפסיקה לאמת אף אחד**, כי הדפדפן משמיט את העוגייה בשקט מכל בקשה, ובלי עוגייה כל בקשה נראית כמו מבקר לא-מחובר. אין הודעת שגיאה, אין קריסה — רק כניסה שלעולם לא "נזכרת".

## מה זה אומר בפועל

- **`DASHBOARD_HOST`** נשאר `127.0.0.1` (ברירת המחדל). אל תשנה אותו כדי "לחשוף את זה החוצה" — זה בדיוק המצב שהפרק הזה מזהיר מפניו.
- מנהרה (למשל Cloudflare Tunnel, ngrok, Tailscale Funnel) או reverse proxy עם תעודת TLS תקפה (למשל Caddy, nginx) הם השכבה שמדברת עם האינטרנט. הם מדברים HTTPS כלפי חוץ ו-HTTP רגיל כלפי `127.0.0.1:4173` (או הפורט שהוגדר ב-`DASHBOARD_PORT`).
- אם ה-proxy עצמו רץ על אותה מכונה, "HTTP רגיל כלפי פנים" הוא תעבורה שלא יוצאת מהמכונה — לא נחשף בפועל.
- אין דרך להריץ את המסך הזה בבטחה בלי שכבה שמסיימת TLS מולו. זו לא תכונה חסרה שתתווסף בעתיד; זו חלוקת האחריות המכוונת: השרת הזה קטן, בלי תלויות רשת, ובלי קוד TLS לתחזק ולתקן.

## שני משתני סביבה שמותר להם לשנות את זה, ורק במפורש

- **`DASHBOARD_ALLOW_PUBLIC_BIND=1`** — בלעדיו, `DASHBOARD_HOST` שאינו loopback גורם לשרת **לסרב לעלות** עם הודעת שגיאה שמסבירה למה. זה השינוי שהפך את הפריסה השגויה שלמעלה מכשל שקט לכשל רועש. אל תגדיר אותו כדי "לעקוף את השגיאה" — הוא קיים למקרה שבו מישהו באמת מסיים TLS בדרך אחרת ויודע בדיוק מה הוא עושה.
- **`DASHBOARD_TRUST_PROXY=1`** — רק כשהדרך **היחידה** להגיע לפורט הזה היא דרך proxy שכותב `X-Forwarded-For` בעצמו. עם הדגל, הכתובת שנרשמת בביקורת של פדיון קוד שחזור היא **הרשומה האחרונה** בכותרת (כל proxy מוסיף את מה שראה, ולכן הימנית היא של ה-proxy הנאמן). בלי הדגל נרשמת כתובת ה-socket עם תווית מפורשת שזו כתובת ה-proxy ולא של הלקוח. כותרת שאפשר לשלוח ישירות לפורט היא טקסט שהתוקף בוחר — ואז הוא זה שקובע מה כתוב ברישום היחיד של אירוע שחזור אישורים.

## סימנים לפריסה שגויה

- ניסיון כניסה שמצליח (החזרת קוד 302 לרשימה) אבל בקשת המשך (`GET /`) חוזרת לעמוד הכניסה — הדפדפן לא שלח את העוגייה, כלומר החיבור לדפדפן אינו HTTPS מקצה לקצה.
- אם יש ספק, יש לבדוק בכלי הפיתוח של הדפדפן (Network) שהתגובה ל-`POST /login` כוללת `Set-Cookie` עם `Secure`, ושכתובת האתר שממנה נטען הדף היא `https://`.

## דשבורד אחד לכל העסקים, וכניסה בכתובת מייל (12/11)

- **תהליך `npm run dashboard` אחד משרת את כל העסקים שעל השרת**, בכתובת אחת (`DASHBOARD_BASE_URL` הוא של השרת). אין כתובת נפרדת לכל עסק.
- **הכניסה היא כתובת מייל**, ייחודית בכל השרת בלי תלות ברישיות, והיא שקובעת לאיזה עסק הבעלים נכנס. שום דבר אחר בבקשה — לא כתובת, לא שדה בטופס, לא כותרת — אינו בוחר עסק. בעל עסק שמנהל שני עסקים צריך שתי כתובות.
- את החשבון יוצרים עם `npm run owner:create -- --business <מזהה> --email <כתובת>`. כתובת שעסק אחר כבר מחזיק נדחית לפני שנשאלת סיסמה.
- **התקנה שעברה מהגרסה של עסק אחד:** מיגרציה 066 שמה בשדה הכניסה את שם המשתמש הישן (בדרך כלל `owner`), ושדה הכניסה בטופס הוא שדה מייל — הדפדפן לא ישלח `owner`. **לפני הכניסה הראשונה** חובה לתת לכל חשבון כתובת: `npm run owner:email -- --business <מזהה> --username <שם> --email <כתובת>` (ראה "מעבר ההתקנה הקיימת" ב-CLAUDE.md). עוגייה מלפני המעבר נקראת כ"לא מחובר" — נכנסים מחדש.
- **עסק מושעה** (`npm run business -- suspend <מזהה>`): אחרי סיסמה נכונה הכניסה אומרת "החשבון מושהה — פנה למנהל המערכת" ולא נפתח סשן; סשן שכבר היה פתוח מסורב בבקשה הבאה. סיסמה שגויה מקבלת את התשובה הכללית, כך שההודעה לא מגלה לזר שהכתובת קיימת.
- **`DATABASE_POOL_MAX`** (ברירת מחדל 20) הוא תקרת הבקשות המקבילות של כל העסקים יחד, יחד עם מה שה-scheduler מחזיק: כל בקשה מאומתת מחזיקה חיבור אחד לבסיס לכל אורכה, גם בקשה איטית שמחכה למודל. תקרה נמוכה מדי נראית כמו מסך שנתקע בעומס, לא כמו שגיאה. להשאיר אותה מתחת למגבלת החיבורים של בסיס הנתונים עצמו.
- **חשבון הבסיס של הדשבורד הוא חשבון האפליקציה** (`DATABASE_URL`, חבר ב-`assistant_app`), לעולם לא `postgres` — ב-Supabase `postgres` עוקף את ההפרדה בין העסקים. החיבור ישיר או session pooler, **לא** transaction pooler.
