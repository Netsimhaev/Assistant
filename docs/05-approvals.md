# סיכון, אישורים ואוטונומיה

---

## 1. סיווג הסיכון

כל פעולה עם תופעת לוואי מנוקדת על **שבעה ממדים**. שישה מהם מחושבים בקוד טהור.

```ts
export interface RiskAssessment {
  actionId: string; actionClass: ActionClass;
  dimensions: {
    money:              { amountMinor: number; pctOfDailyCeiling: number; score: number };
    reversibility:      { class: 'trivial'|'reversible'|'costly'|'irreversible'; score: number };
    externalVisibility: { audience: 'internal'|'one_known'|'one_unknown'|'many'|'public'; score: number };
    dataSensitivity:    { classes: DataClass[]; leavesInstance: boolean; score: number };
    novelty:            { metric: NormMetric; z: number; precedentIds: string[]; score: number };
    provenance:         { level: TrustLevel; chainDepth: number; score: number };
    charterFit:         { verdict: 'within'|'ambiguous'|'violates'; citedRuleIds: string[]; score: number };
  };
  total: number;                                   // משוקלל, 0–100
  band: 'routine' | 'sensitive' | 'anomalous' | 'blocked';
  decidedBy: 'rules' | 'rules+haiku' | 'rules+opus';
  explanation: string;                             // משפט אחד לבוס
  suggestedApprovers: string[];
}
```

### רצועות

| רצועה | תנאי | ניתוב |
|---|---|---|
| `routine` | סה"כ < 25 **וגם** `charterFit=within` **וגם** אף ממד לא מוקסם | בצע; רישום בלוג בלבד |
| `sensitive` | 25–60, או כסף מעל תקרת המחלקה, או מגע ראשון עם גורם לא מוכר | אישור, timeout רגיל |
| `anomalous` | חריגות z > 3, או `charterFit=ambiguous`, או `provenance=open_web` עם כל הוצאה | אישור עם הדגשת החריגה, timeout קצר, הסלמה ב-timeout |
| `blocked` | פרדיקט `forbidden` קשיח, הפרת תקרת מקור, או תקציב מוצה | דחה; הודע; **לעולם לא להציע כפתור אישור** |

### כשההוראה של הבעלים היא האישור עצמה

בעל העסק שנוקב בעצמו בשם הנמען, בנושא ובגוף ההודעה — נותן את האישור באותה נשימה שבה הוא נותן את ההוראה. זה חוסך כרטיס אישור נפרד **רק** כשמתקיימים שלושה תנאים חיוביים (המימוש מתועד ב-CLAUDE.md, "הפטור ממגע ראשון"):

1. **הבעלים עצמו** יזם את המשימה;
2. שום צעד בתוכנית הנוכחית לא קרא תוכן שמקורו מחוץ להתקנה — לא דף אינטרנט, לא מייל נכנס, לא רשומת CRM;
3. המשימה **מעולם** לא קראה תוכן כזה, גם לא בתכנון קודם שהוחלף בתכנון מחדש.

**מה מבטל את הפטור.** כל תוכן חיצוני שנקרא לאורך חיי המשימה — פעם אחת מספיקה, ולעולם לא מתאפסת. "תקראי את המייל מדנה ותעני לה" **אינה** זכאית לפטור: ההוראה מהבעלים, אבל תוכן התשובה — ואולי הכתובת — הגיעו ממי שכתב את המייל.

**מה שהפטור לא רואה.** אם הבעלים עצמו מעתיק־מדביק או מקליד מחדש את מה שמישהו אחר כתב, שום כלי קריאה לא רץ והדגל לא נדלק — התוכן הזר "נכנס" בלי שהמערכת ראתה קריאה. הפטור מגן מפני תוכן שהעוזרת *קראה בעצמה*, לא מפני תוכן שהבעלים בחר להעביר הלאה במילים שלו. חשוב לדעת את הגבול הזה: הוא לא נסגר בקוד, והוא לא ייסגר בעתיד הקרוב.

**הפטור לבדו אינו מבטל אישור — וכיום הוא אינו נגיש בפועל, לאף מחלקה.** מה שהוא עושה: מוריד את רצועת הסיכון ממגע-ראשון מ-`sensitive` ל-`routine`, בשלב 10 של השער (`assessRisk`). הפעולה עדיין דורשת אישור אם **התקרה של המחלקה בתקנון** קובעת `approve_required`, או אם המחלקה שייכת לרשימת "לעולם לא אוטונומית לחלוטין" (תשלום, החזר, חוזה, ייצוא נתונים) — שם התקרה גוברת בפני עצמה בלי קשר לרצועה.

אבל הסיבה שאף פעולה לא זוכה לפטור היום חזקה יותר מהתקנון של מחלקה זו או אחרת: שלב 8 של השער (אוטונומיה) רץ **לפני** שלב 10, ובודק `effectiveAutonomy` — המינימום מבין כל התקרות שחלות, כולל רמת הרמפה שנטענת מ-`autonomy_ramp`. `RAMP_FLOOR` (`src/orchestrator/ramp.ts`) הוא `draft_only` לכל מחלקה שאין לה שורת רמפה, ואין קידום אוטומטי — `setRampLevel` נקרא מסקריפט CLI ידני בלבד (`npm run ramp:set`, ו-`cli/seed-job.ts` למחלקה אחת ולמטרות בדיקה) ומתוך מבחנים. כל עוד הרמפה עומדת על `draft_only`, שלב 8 דוחה (`draft_only:persist_as_draft`) לפני ששלב 10 בכלל רץ — בלי קשר למה שהתקנון קובע לאותה מחלקה.

**מחלקה אחת הועלתה בפועל (10/09): `email.reply` ל-`auto_notify`.** זו המחלקה היחידה שבה כל התקרות מעליה גבוהות מהרמפה — בסיס `auto_notify` בתקנון, `auto` לפרובננס `boss` — **וגם** יש מאחוריה מתאם שעושה משהו. התוצאה: מענה יוצא בשרשרת שהבוס פתח, אל צד-שיח שהתקנון מכיר, רץ בלי כרטיס. `known_counterparty` נשאר `approve_required`, ו-`unknown_external`/`open_web` נשארים `draft_only` — כלומר מסמך שהגיע מבחוץ עדיין אינו יכול לגרום לשליחה אוטונומית, וזה נכון מבנית ולא במקרה. `src/orchestrator/ramp-raise.test.ts` נועל את שני הצדדים מול התקנון הלא-מעורך.

**ותנאי נוסף שההעלאה חשפה, ולא היה מתועד בשום מקום:** נמען של מחלקה שפונה ל-`person` נפתר **לפי הכתובת בלבד** — `counterpartyId` אינו יכול לעמוד במקומה. כלומר גם אחרי העלאת רמפה, שליחה אוטונומית דורשת שהתקנון יכיר את **הדומיין** של הנמען, או שההוראה תנקוב בכתובת (ואז ההרשאה העומדת מכסה). כל עוד `boss` היה פטור ממגע ראשון זה לא הורגש באף מבחן, ורוקון הרשימה הפיל 28 מבחנים שרכבו על הפטור בלי לדעת.

יוצא דופן ידוע אחד: `cli/seed-job.ts` מעלה בפועל את `email.initiate` ל-`approve_required` בעסק שהוא רץ בו, כדי להדגים את שרשרת הביצוע. שם שלב 8 אכן מעביר הלאה, אבל הבלימה עוברת למקום אחר באותו שער: `needsApproval` דורש אישור כש-`effective === 'approve_required'`, ללא קשר לרצועת הסיכון — כך שגם אם הפטור יחושב שם ל-`true` ויוריד את הרצועה מ-`sensitive` ל-`routine`, האישור עדיין נדרש.

כדי שהוראת בעלים על פנייה ראשונה תספיק **מקצה לקצה**, בלי שום כרטיס, דרושות שתי החלטות נפרדות — לא אחת: רמפה אמיתית שמעלה את המחלקה הרלוונטית מעל `draft_only`, **וגם** הבעלים מוריד בחתימה את הבסיס של אותה מחלקה בתקנון (למשל `email.initiate` ל-`auto_notify`). זו החלטה בחתימה, לא שינוי קוד — והתקנון המרונדר מציג אותה גלויה.

### ציווי הבוס: שאלה אחת שמאשרת, וגוברת על הכול (28/10)

**מאז 28/10 הוראה של הבעלים שיש בה פעולה אינה רצה ישר, ואינה נבלמת בתקרות שלמעלה — היא שואלת שאלה אחת.** כל מה שבסעיף הקודם נשאר נכון לתוכנית שרצה **בלי** שאלה; מה שהשתנה הוא שתוכנית של הוראה שיש בה צעד מסווג אחד לפחות כבר אינה רצה כך. היא חונה (פאזת `plan`), והבעלים מקבל, באותו ערוץ שבו כתב, שאלה שמציגה **כל** שדה של **כל** צעד שעומד לרוץ — נמען, נושא, גוף מלא, סכום, וכל שדה נוסף — בלי חיתוך. "כן" מוקלד (לא הקלטה, לא כיתוב של תמונה), שהגיע אחרי ההצגה ובתוך 30 דקות, מאשר; כשהשם עמום בין שניים או שלושה אנשים, השאלה ממוספרת והבחירה היא האישור. תוכנית של קריאות בלבד ("מה דנה כתבה") רצה כמו קודם, בלי שאלה.

**הצעד שאושר עובר את השער דרך פטור משלו, `confirmedCommandCovers`, שמדלג על שלבים 5–10 — גם `approve_required` בתקנון, גם "לעולם לא אוטונומית לחלוטין", גם המתג ב-`off`.** הבעלים ראה את הבייטים ואמר כן; תקרה שנועדה לבלום את העוזרת אינה בולמת אותו. ובהכרעה מפורשת (28/10): גם איסורי `forbidden`, רשימת "אל תפנה", שעות שקט ותקרות התקציב. **נשארים:** מתג העצירה, תקנון קריא, כלי שקיים ושמותר לסוכן (ולכן תשלום וחתימה עדיין לא — אין להם כלי), וסכום שלא נקרא. האישור חל רק על הבייטים שהוצגו — עריכה בלתי אפשרית, שינוי פירושו הוראה חדשה — רק לתוכנית שנבחרה, רק ל-24 שעות, ורק פעם אחת לכל צעד: השער **תובע** כל צעד לפני שהוא יוצא, ותביעה שנייה מסורבת. כשל לא-ודאי אחרי האישור לא נשלח שוב בשקט — הבעלים נשאל שוב, רק על מה שלא בוצע, עם "ייתכן שזה כבר בוצע — לבצע שוב?". הפירוט, כולל כל תנאי והמחיר של כל הכרעה, ב-CLAUDE.md ("ציווי הבוס").

## 2. זיהוי חריגות מול ההיסטוריה של העסק

זו הדרישה "לקרוא את אופי העסק" בצורתה הנמדדת.

```ts
export type NormMetric =
  | 'order_qty_for_sku'          // 50 יחידות מול p50=20, p95=30 → z גבוה
  | 'order_value_for_supplier'
  | 'discount_pct_for_customer'
  | 'quote_value_for_segment'
  | 'outbound_volume_per_day'
  | 'reply_length_for_channel'
  | 'first_contact_hour'
  | 'new_counterparty_rate';
```

`NormsEngine` מתחזק התפלגויות מתגלגלות (חלונות 30/90/365 יום) ב-Postgres, מחושבות מדי לילה.

> **סטטיסטיקה עמידה: חציון + MAD, לא ממוצע + סטיית תקן.** נתוני עסק הם heavy-tailed, והממוצע נגרר אחרי חריגים בודדים.

**התחלה קרה:** ב-60 הימים הראשונים *הכל* חריג. זו **התנהגות נכונה, לא באג** — מנגנון הרמפה (סעיף 5) שומר על אוטונומיה נמוכה ממילא בתקופה הזו.

> **סיכון שנלקח ביודעין, ונסגר ב-10/09.** `novelty` מחזיר `z=0` תמיד עד ש-`NormsEngine` קם בשלב 2 — אין עדיין היסטוריה למדוד מולה. במקביל, פטור מגע-ראשון (`FIRST_CONTACT_EXEMPT` ב-`policy/risk.ts`) הוציא פנייה שהבוס יזם ישירות מהסלמת `one_unknown`. שתי העובדות יחד אמרו שפנייה חדשה שהבוס יזם עברה כשאף אחד משבעת הממדים לא עוצר אותה, ורמפת האוטונומיה (סעיף 5) הייתה הבלם היחיד שנשאר — ורק כי כל מחלקה התחילה ב-`draft_only`. **ב-10/09 הבלם ההוא הוסר מ-`email.reply`, ובאותו יום נמדד מה שנשאר מתחתיו:** מענה בשרשרת שהבוס פתח יצא **גם אל כתובת שאיש לא ערב לה**, בלי כרטיס. בעקבות זה רוקנה רשימת הפטור — `boss` היה החבר היחיד בה — כך שהסלמת "נמען שאינו נפתר" חלה עכשיו על כל מקור בלי יוצא מן הכלל, ו-`novelty` באפס כבר אינו הממד היחיד שעומד בדרך.
>
> **מה שהבעלים רצה מהפטור לא אבד, והוא מבוטא עכשיו במקום שיודע לבטא אותו.** הכלל שנקבע הוא שנמען שהבעלים **הקליד** נחשב מוכר — וזו בדיוק ההרשאה העומדת שדלת ההוראה כותבת, שמבטלת את אותו איבר עצמו ב-`needsApproval` עבור הנמענים שההוראה נקבה בהם, ולא מעבר להם. `provenanceChainDerived` יכול לומר רק שהשרשרת באה מהבעלים, לעולם לא שהבעלים בחר את הכתובת הזו — ומבין השניים, רק השני היה רצוי אי-פעם. `src/orchestrator/ramp-raise.test.ts` מחזיק את שני הצדדים על אותה כתובת בדיוק: בלי מענק — כרטיס; עם מענק — שליחה.
>
> **המנגנון נשמר ולא נמחק.** התנאי עדיין קורא את הרשימה ועדיין דורש `provenanceChainDerived`, כך שהחזרה היא שורה אחת אם החיכוך יתברר כגרוע מהחשיפה. שני מבחנים ב-`src/policy/positive-controls.test.ts` עוברים על כל רמות האמון ונופלים — בשם הרמה — ברגע שמישהו יחזיר חבר לרשימה.

> **החוקים המוצהרים (התקנון) והנורמות הנצפות (הפרופיל) נפרדים בכוונה.**
> התקנון אומר מה **מותר**. הפרופיל אומר מה **רגיל**.
> פעולה יכולה להיות מותרת לחלוטין ועדיין לדרוש מבט שני.

## 3. תור האישורים

```ts
export interface ApprovalRequest {
  id: string; jobId: string; envelopeId: string;
  actionClass: ActionClass;
  summary: string;              // שורה אחת, בגודל התראת טלפון, בעברית
  detail: string;               // גוף הכרטיס
  diffVsNorm?: string;          // "כמות 50 — בדרך כלל 20"
  artifacts: EvidenceRef[];     // טיוטת הטקסט, צילום העגלה, PDF ההצעה
  risk: RiskAssessment;
  proposedCall: { tool: string; input: unknown; inputHash: string };
  requestedFrom: { personId: string; channel: Channel }[];
  createdAt: string; expiresAt: string;
  onTimeout: 'expire' | 'escalate_next' | 'notify_only';
  state: 'pending'|'approved'|'approved_with_edit'|'denied'|'expired'|'cancelled';
  decision?: {
    by: string; at: string; channel: Channel; note?: string;
    editedInput?: unknown;
    inputHashAtDecision: string;   // שומר TOCTOU
  };
}
```

### הכרטיס נושא את מילות ההצעה, לא רק את הסיכון

`summary`/`detail` על הכרטיס כבר לא באים תמיד ממנוע הסיכון בלבד. כש-`GateContext.proposalText` נמסר לשער (`src/policy/engine.ts`) — הכותרת והתיאור שהמתכנן כתב, "אשלח מייל לדנה" ולא "פעולה בסיכון sensitive" — הם ממלאים את שני השדות האלה. `risk.explanation` **לא נמחק ולא הוחלף**: הוא נשאר בשורת הסיכון של הכרטיס בדיוק כפי שהיה, כי הבוס צריך גם מה מוצע וגם למה המערכת חוששת — שתי עובדות נפרדות, לא אחת שמסתירה את השנייה. כשאין הצעה — כרגע הרוב המכריע של הקריאות, ראה `docs/09-roadmap.md` — `summary`/`detail` נופלים בחזרה למשפט הסיכון ולתיאור ברירת המחדל, בדיוק כמו לפני.

**המייל, בכוונה, לא מקבל את מילות ההצעה.** `src/governance/notify.ts` ממשיך לבנות את הנושא והגוף מ-`risk.explanation` ומתווית שהגייט עצמו בנה (`כלי · מחלקת פעולה · רצועה`), ולעולם לא מ-`request.summary`/`request.detail`: תיבת הדואר פחות מהימנה מהדשבורד, ומילים שמקורן במודל שקרא תוכן חיצוני לא אמורות לרכוב על הודעה שיוצאת ממנה. מילות ההצעה מחכות מאחורי ההתחברות, על הכרטיס עצמו.

### שלושת ערוצי המסירה — כרטיס החלטה זהה בכולם

| ערוץ | תפקיד | נימוק |
|---|---|---|
| **דשבורד PWA + Web Push** | ראשי | שליטה מלאה בכרטיס, ראיות מלאות לנגד העיניים, אישור מרוכז לפריטים מאותה מחלקה, והיסטוריית ביקורת. אפס תלות בצד שלישי ואפס עלות להודעה. **כל החלטה שכרוכה בכסף אמיתי מוכרעת כאן** |
| **WhatsApp דרך הגשר** | התראה דחופה בנייד | הבוס כבר שם. הגשר שולח חופשי בכל זמן. **מענה בטקסט או במילת מפתח, לא בכפתורים** — כפתורים אינטראקטיביים אינם אמינים בלקוחות לא-רשמיים. הכרטיס מציג "השב 1 לאישור / 2 לדחייה / 3 לפרטים" ובנוסף קישור עמוק לדשבורד |
| **מייל עם קישורי HMAC** | גיבוי | קישורי approve/deny חתומים, nonce, TTL קצר. עצמאי לחלוטין. **לעולם לא הערוץ היחיד** — אישור במייל איטי מדי |

> **מסלול האישורים לעולם לא תלוי ב-WhatsApp.** הגשר הוא הערוץ השביר ביותר במערכת. הדשבורד והמייל חייבים להיות עצמאיים באמת, כך שאם הגשר יורד המערכת ממשיכה לתפקד במלואה ורק ההתראה בנייד נעלמת.

### "חתום ואשר" — תוצאה שלישית, רק כשיש מסמך מאחורי הבקשה

לצד **אישור** ו**דחייה**, כרטיס שיש לו מסמך מאחוריו (`docs/superpowers/specs/2026-09-01-signature-design.md`) מציג כפתור שלישי: **חתום ואשר**. הכפתור עצמו מותנה — הוא מופיע רק כשהשרשרת `approval_requests.job_id → proposals.job_id`, ומשם `proposals.reading_id → document_readings.document_id → documents` (`src/dashboard/document-for-approval.ts`) מוצאת מסמך; רוב האישורים, כמו שליחת מייל, אינם נושאים אחד ולא מציגים אותו. `proposals` נושאת עמודת `job_id` רק ממיגרציה `018_proposal_job.sql` — שורה שנכתבה לפני שהעמודה קיימת אינה ניתנת לאיתור אחורה, והכפתור לא יופיע גם עבורה.

> **רדום: הכפתור אינו יכול להופיע בהתקנה רצה היום.** הנתיב, הרשומה והפקד בנויים ומכוסים במבחנים — ואף על פי כן אין דרך להגיע אליהם בייצור. `documentForApproval` דורשת שורת `proposals` עם `job_id`; `saveProposal` נקראת בייצור רק מ-`proposeForReading`, שנקראת רק מ-`src/sdk/run-propose.ts` — סקריפט ידני שמעולם לא הורץ חי. עד שייכתב קורא בייצור שיוצר את שורת ההצעה, כל אישור הוא אישור בלי מסמך, הכפתור אינו מרונדר, ואף חתימה לא נכתבה. מה שחסר הוא **הכותב של ההצעה**, לא קוד החתימה.

**זו לא זרימה מקבילה.** "חתום ואשר" מגיע לאותה `state: 'approved'` שאישור רגיל מגיע אליה, ולפני כן בלבד: מגבב מחדש את הקובץ **מהדיסק**, לא מקריאת `documents.sha256` שנשמרה בקליטה (`verifyDocumentUnchanged`, `src/documents/verify.ts`), ומשווה. אי-התאמה — **סירוב**, עם סיבה בעברית, והאישור נשאר `pending` כדי שהבעלים יתקן ויחזור. מסמך שהשתנה מאז שנקרא הוא מסמך שהבוס לא ראה; חתימה על הגיבוב הישן הייתה מייצרת רשומה שמעידה על קובץ אחר מזה שיושב על הדיסק.

`handleDecision` (`src/dashboard/server.ts`) מסרב גם במקרים נוספים, לפני שהוא נוגע בקובץ בכלל: אישור שאינו `pending` או שפג תוקפו (אותם פרדיקטים בדיוק ש-`decide` אוכף) — בלי הבדיקה הזו, טאב ישן היה יכול לכתוב חתימה קבועה על אישור שכבר **נדחה**; ובקשה בלי מסמך בכלל, כי הנתיב עצמו מסרב גם אם מישהו פונה אליו ישירות בעקיפת הכפתור.

**החתימה, שורת הביקורת שלה וההחלטה הן טרנזקציה אחת.** `decideAndSign` (`src/governance/sign-decision.ts`) מריץ את שלושתן על חיבור אחד, ו-`decide` אחרון: הוא המשפט שעדיין יכול לסרב על `state = 'pending' AND expires_at > now()`, ולכן הסירוב שלו מגלגל אחורה את החתימה ואת שורת הביקורת. בשלושה commits נפרדים, דחייה בטאב שני או פקיעת תוקף בין הבדיקה לבין `decide` השאירו שורת `signatures` קבועה שמעידה על אישור שנדחה — ומסמך שאי אפשר לחתום עליו לעולם, כי הייחוד תופס. הבדיקה המוקדמת בנתיב מקטינה את החלון ואינה סוגרת אותו. המעבר של ה-job (`resumeAfterDecision`, `src/orchestrator/resume.ts`) רץ אחרי ה-commit, כי `transition` פותח טרנזקציה משלו.

**מה שהבעלים רואה לפני שהוא לוחץ.** שם הקובץ **ו**-12 התווים הראשונים של `documents.sha256`. שם הקובץ נשמר מילה במילה מהשולח, ותווי כיווניות (U+202E ומשפחתו) יכולים לגרום לו להיראות אחרת ממה שהוא — `escLabel` מסיר אותם לשדה הזה בלבד. הגיבוב מחדש עונה "האם אלה אותם בייטים"; בלי הצגת הגיבוב, שום דבר בכרטיס לא עונה "**אילו** בייטים".

**מה שנכתב.** גיבוב שמדד ברגע החתימה (לא הגיבוב שנקלט), מזהה האישור, ושם משתמש הדשבורד שביצע — לעולם לא מזהה סוכן ולעולם לא `'system'`, כי אדם הוא שחתם (`recordSignature`, `src/governance/signatures.ts`, מיגרציה `019_signatures.sql`). ייחוד על `(business_id, document_id)`: מסמך נחתם פעם אחת, וחתימה שנייה מסורבת ברעש במקום לשכתב בשקט מי אישר ומתי. שורת ביקורת נפרדת נכתבת מסוג `signature` — נבדל מ-`approval` בכוונה, כדי שקורא במסלול הביקורת יבחין בין "הבוס אישר פעולה" לבין "הבוס קיבל מסמך כמחייב". החתימה השנייה שנדחית אומרת **מתי ומי** חתם, לא רק שכבר נחתם. ומיגרציה `020_signature_evidence.sql` הופכת את מפתח הזר ל-`ON DELETE RESTRICT` ומוסיפה `CHECK` על צורת הגיבוב: מחיקת מסמך לא גורפת איתה את הראיה שאדם קיבל אותו כמחייב.

### שומר TOCTOU

האישור **נקשר ל-`inputHash`**. אם הקלט השתנה בין הבקשה להחלטה — למשל המחיר באתר הספק זז — ה-hash לא תואם וה-`PreToolUse` דוחה מחדש. אישור-עם-עריכה קושר את עצמו לקלט **הערוך**, וזה מה שמאפשר לבוס לשנות כמות בכרטיס ולראות את השינוי מבוצע נאמנה.

שלוש רמות. **כולן חייבות לשרוד restart של התהליך** — המצב יושב ב-Postgres ונבדק בראש כל `PreToolUse` וגם על ידי צרכן התור לפני כל dequeue.

| רמה | טריגר | אפקט |

| **עצירת מחלקה** | פקודת הבוס, או 3 אירועים בשעה באותה מחלקה | הצעדים של אותה מחלקה מפסיקים לצאת מהתור; ה-jobs נרדמים |

## 5. אוטונומיה נרכשת — התשובה ל"כמה חבל לתת"

**מנגנון הקידום נבנה (22/09).** מה שסעיף זה תיאר בעבר — דגימות ב-30 יום, אחוזי הסכמה, ירידה שדורשת חודש נקי כדי לחזור — היה מפרט, לא קוד. הסעיף מתאר עכשיו את מה שרץ בפועל: מתג אחד לעסק, מדידה נגזרת, ומדרגה מורווחת אחת בכל הסולם.

### המתג

בעל העסק בוחר מצב אחד לעסק, לא הגדרה לכל מחלקת פעולה בנפרד — התקנון החתום כבר שולט ברמת המחלקה, ומערכת הגדרות שנייה לצידו הייתה יכולה לסתור אותו.

```ts
export const AutonomyMode = z.enum(['off', 'ask', 'learn']);
```

| מצב | רצפת הרמפה | תקרת הרמפה | קידום אוטומטי |
|---|---|---|---|
| `off` | `draft_only` | `draft_only` | לא |
| `ask` | `approve_required` | `approve_required` | לא |
| `learn` | `approve_required` | `auto_notify` | כן |

`off` הוא ברירת המחדל של התקנה חדשה. הבעלים משנה את המתג ממסך `/autonomy` בדשבורד — מאחורי הסשן שלו ומאחורי אסימון CSRF, אותו שער בדיוק שדרכו עוברות חתימה ומחיקה — ו`setAutonomyMode` ([src/governance/autonomy-mode.ts](../src/governance/autonomy-mode.ts)) רושם שורת ביקורת שנושאת את המצב הקודם, החדש, ואת מי ששינה. **המתג לא דורש חתימה על תקנון חדש**, כי הוא לא יכול להרחיב את מה שהתקנון מתיר — הוא רק קובע כמה נמוך מותר לרמפה הנרכשת לשבת. `rampBoundsForMode` נותן לכל מצב **רצפה וגם תקרה**: הרצפה מאפשרת למחלקה חדשה להתחיל לפעול, והתקרה היא מה שהופך `off` לעצירה אמיתית — בלעדיה, מחלקה שכבר קודמה הייתה ממשיכה לפעול גם אחרי שהבעלים סובב את המתג אחורה.

**זו הרפיה של תקרה אחת מתוך חמש, ולכן היא בטוחה.** `effectiveAutonomy` (`src/policy/engine.ts`) מצרף חמש תקרות במינימום — בסיס המחלקה בתקנון, תקרת הפרובננס, חריגים לפי צד-שיח, תקרת הרמפה, ותקרת המעטפה — והראשונה תמיד נוכחת. תקרת הפרובננס נוכחת גם היא, חוץ משני חריגים בשמם, שניהם ל-job מענה של תיבת המייל בלבד: מענה שהבעלים אישר (`approvedReplyCovers`, שמשמיט אותה יחד עם הרמפה), ומענה שנלמד (`learnedReplyCovers`, שמשמיט רק אותה, ורק כשהמתג על `learn` ו-`email.reply` קודמה — ראה "מענה שנלמד" למטה). סוג פעולה שהתקנון קיבע ב-`approve_required` נשאר שם גם כשהרמפה מצביעה על `auto_notify`; `src/orchestrator/ramp-floor.test.ts` מוכיח את זה דרך החלטת שער אמיתית.

### המדידה והקידום

בכל הערכה, לכל מחלקת פעולה, המערכת שואלת את `approval_requests` ישירות — לא סופרת בעמודה נפרדת (`agreementFor`, [src/governance/agreement.ts](../src/governance/agreement.ts)). זה **מצב הצל** (26/10): העוזרת מציעה, הבעלים מכריע, ולכל הכרעה נגזר פסק — "צדקה", "לא צדקה" או "לא נספר" — בפונקציה טהורה אחת, `agreementVerdict` ([src/governance/agreement-verdict.ts](../src/governance/agreement-verdict.ts)), שגם המסך וגם הקידום קוראים:

- `approved` — צדקה. `denied` — לא צדקה. `expired`/`cancelled` — לא נספרים, כי איש לא ענה או שהבקשה בוטלה.
- `approved_with_edit` — צדקה **רק** אם השינוי קל: קבוצת הנמענים זהה, **כל מספר זהה ובאותו סדר** (שני סכומים שהוחלפו ביניהם, או `12/11` מול `11/12`, הם שינוי), כל מילת תאריך זהה (ימי השבוע, היום/מחר/מחרתיים/אתמול, חודשים, `יום ג'`), ומרחק העריכה ברמת מילים על הנושא והגוף הוא **עד שלוש מילים**. שינוי בנמען, במספר או בתאריך הוא תמיד "לא צדקה", גם כשזו מילה אחת.

**מה נחשב ראיה.** רק כרטיס של **job מענה של תיבת המייל** — כרטיסי דלת ההוראות והמנצח חולקים את המחלקה אבל אינם הצעת מענה של העוזרת, וכרטיס המנצח אינו מבצע דבר כשמאשרים אותו. מכל job נספר רק **הכרטיס הראשון שהוכרע**; כרטיס שהועלה מחדש אחרי שליחה שנכשלה מדולג, כי הוא כבר נושא את הטקסט של הבעלים. החלון הוא **14 הימים האחרונים, או מאז המעבר האחרון של המחלקה — המאוחר מביניהם**.

**יותר מ-80% "צדקה" מתוך לפחות חמש הכרעות, במצב `learn`, על מחלקה שעדיין `approve_required`** — מקדמים אותה למדרגה אחת ויחידה: `auto_notify`. "מעל" ולא "שווה": בחמש הכרעות פירושו חמש מחמש. זו המדרגה המורווחת היחידה בכל הסולם, ומשתי סיבות מבניות: `draft_only → approve_required` הוא מעשה של הבעלים בלבד, כי כש-`effectiveAutonomy` מחזיר `draft_only` השער דוחה בשלב 8 וחוזר — אין כרטיס, אין דגימה; ו-`auto_notify → auto` לא נבנה, כי שתי הרמות זהות באכיפה (`needsApproval` בודק רק `effective === 'approve_required'`). `MIN_SAMPLES = 5`, `LEARNED_THRESHOLD = 0.8` ו-`AGREEMENT_WINDOW_DAYS = 14` הם נקודות כיול מוצהרות, לא נמדדות. נימוק הקידום נרשם בשורת `autonomy_events`: "N מתוך M הכרעות אחרונות (X%)". מסך "רמת הלימוד" ב-`/autonomy` מציג את אותם מספרים — ציון כולל וכרטיס לכל מחלקה.

**היום רק `email.reply` יכולה לצבור ראיות.** למחלקות אחרות (פגישות, וואטסאפ ללקוחות, CRM) עוד אין מקור ראיות — אף כרטיס שלהן אינו נספר, והכרטיס שלהן במסך נשאר על "עוד מוקדם לדעת (0 מתוך 5)".

### מענה שנלמד ועדכון על כל פעולה

כשמענה למייל נכנס נלמד, הוא יוצא **בלי כרטיס** — גם שהמייל הגיע מבחוץ (הכרעת הבעלים H10). `learnedReplyCovers` ([src/policy/learned-reply.ts](../src/policy/learned-reply.ts)) משמיט את תקרת המקור בלבד, ורק כשהמחלקה היא בדיוק `email.reply`, הרמפה המהודקת `auto_notify`, הנמען הוא כתובת אחת ששווה ל-From השמור, אין סכום ואין צרופות, ולמשימה אין שליחה שתוצאתה לא ידועה. רצועת הסיכון נשארת: שולח שהתקנון אינו מכיר עדיין מקבל כרטיס. הפירוט, והסיכון המוצהר של From מזויף, ב-`CLAUDE.md` וב-[08-risks.md](08-risks.md).

על **כל** צעד שבוצע בלי כרטיס — פנימי או חיצוני, חוץ ממה שהבעלים הורה עליו בהוראה — נשלח עדכון אחד, לעולם לא מקובץ (`dispatchActionUpdates`, [src/orchestrator/action-updates.ts](../src/orchestrator/action-updates.ts)), בערוצים שהבעלים בחר (וואטסאפ / מייל / מסך, לפחות אחד), עם קישור למסך הפעולות העצמאיות שבו מסמנים "זו הייתה טעות".

### ירידה בדרגה

שני אותות עצמאיים, ושניהם מורידים מיד ל-`approve_required` — אין סף ואין צבירה, והמדידה מתחילה מחדש מרגע ההורדה:

- **סימון של הבעלים** — כפתור "זו הייתה טעות" במסך הפעולות העצמאיות (`/autonomy/actions` בדשבורד, [src/dashboard/autonomous-actions.ts](../src/dashboard/autonomous-actions.ts)) — כל צעד שרץ בלי כרטיס אישור מאחוריו.
- **משימה שהסתיימה ב-`failed`** תחת מחלקה שרצה מעל `approve_required` — הרשת מתחת לטעות שיפוט שהבעלים לא סימן, גם כשהעדכון הגיע אליו.

מחלקה שירדה **פעמיים** נעצרת ומחכה להחלטה מפורשת של הבעלים; `demotionCount` נגזר מספירת שורות `autonomy_events` ולא ממונה שמתוחזק בצד. חלון הזמן שכל אות נבדק כנגדו הוא **מאז המעבר האחרון** של המחלקה (עלייה או ירידה) — לא מתחילת הזמן — כדי שההכרעות שהעלו אותה לא ימשיכו "לספור" נגד ירידה, ולא ימשיכו לקדם אותה מחדש בסבב הבא.

### התיקון כלמידה

עריכה לפני אישור וסימון בדיעבד הן שני מעשים מובנים של הבעלים, ולכן נכתבים בלי קריאה למודל: `recordCorrection` ([src/governance/corrections.ts](../src/governance/corrections.ts)) כותב שורת זיכרון מסוג `preference` על צד-השיח שהצעד המתוקן היה פונה אליו, תחת פרובננס `boss` — נגזר מפתיחת job חדש שהתיקון פותח בעצמו, לא מהמשימה שהצעד המקורי שייך לה — כך שתיקון על כרטיס שנולד ממסמך חיצוני לא מאבד את מעמדו. תיקון חדש דורס ישן על אותו צירוף (צד-שיח, מחלקת פעולה) באמצעות אותו אינדקס ייחודי חלקי שכבר עוצר הצטברות זיכרון בלתי מוגבלת. **תיקון משפיע על ניסוח, לעולם לא על הרשאה** — אינו הופך למקור סמכות לפנות למישהו חדש.

### איפה זה רץ

פס אחרון ב-`schedulerPass` (`evaluateAutonomy`, [src/orchestrator/promote.ts](../src/orchestrator/promote.ts)), **אחרי** `tick`, `runDueJobs` ו-`closeVerifiedJobs` — כי הוא צורך את מה שהסבב הזה עצמו ייצר: כרטיס שהוכרע, משימה שנכשלה. כשל בהערכת מחלקה אחת מבודד ואינו עוצר את השאר או את הסבב.

## 6. מסלול הביקורת

טבלה אחת, append-only ומשורשרת-hash, שמשמשת גם כזיכרון האפיזודי (L2) וגם כרשומת התאימות.

```ts
export interface AuditEntry {
  seq: bigint;                    // מונוטוני
  at: string;
  jobId?: string; envelopeId?: string;
  actor: AgentId | 'orchestrator' | 'human' | 'system';
  onBehalfOf?: string;            // personId כשאדם החליט
  kind: 'intent_to_act' | 'tool_call' | 'tool_result' | 'decision' | 'approval'
      | 'policy_denial' | 'phase_change' | 'memory_write' | 'incident' | 'charter_change';
  actionClass?: ActionClass;
  charterVersion: string;
  provenance: TrustLevel;
  risk?: RiskAssessment;
  inputHash: string; outputHash?: string;
  artifacts: EvidenceRef[];
  costMinor?: number; tokens?: { in: number; out: number; cacheRead: number };
  prevHash: string; hash: string;  // sha256(prevHash || canonical(entry))
}
```

### התכונות שחשובות

- **הכוונה נרשמת לפני הקריאה**, כך שקריסה באמצע פעולה נראית לעין
- **שרשרת ה-hash** הופכת שיבוש לניתן לזיהוי
- כל רשומה נושאת את **גרסת התקנון**, כך שאפשר לענות "מה היו החוקים כשזה קרה?"
- הכל ניתן לתשאול **בשפה פשוטה** מהדשבורד — "הראה לי כל מה שהעוזרת עשתה עבור לקוח X"

שימור לפי `charter.data.retentionDays`, עם עקיפת legal-hold.
