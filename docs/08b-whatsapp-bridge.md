# גשר הוואטסאפ

מסמך נפרד כי זו הנקודה הכי שברירית בארכיטקטורה, וכי ההחלטה שהתקבלה כאן שונה ממה שהיה מומלץ בברירת מחדל.

---

## 1. הדרישה ולמה היא כופה את הפתרון

**הדרישה התפקודית:** העוזרת מתכתבת חופשי עם כל אחד מאנשי הקשר של הבוס, בכל זמן, בלי מגבלת תבניות.

הדרישה הזו **אינה ניתנת למימוש ב-API הרשמי של Meta בשום תצורה**:

- מחוץ לחלון 24 השעות מההודעה האחרונה של הנמען, ה-Cloud API מתיר **רק תבניות מאושרות מראש**
- יזום שיחה מול אדם חדש הוא **תמיד** תבנית
- כל נמען חייב opt-in מוקדם לפי מדיניות ההודעות של WhatsApp

**גם Zapier לא פותר את זה.** האפליקציה הרשמית `WhatsApp Business` ב-Zapier היא עטיפה מעל אותו Cloud API ויורשת את כל מגבלותיו. ספקים חיצוניים על Zapier עוטפים את הפרוטוקול הלא-רשמי — כלומר אותו סיכון בתוספת שני מתווכים בנתיב של כל הודעה, בהשהיה של דקות ובתמחור לכל task.

**המסקנה: המסלול היחיד שעונה על הדרישה הוא גשר לא-רשמי.**

---

## 2. ההפשטה — `WhatsAppGateway`

לפני בחירת ספק, מגדירים ממשק. זה מה שהופך את הבחירה להפיכה.

```ts
export interface WhatsAppGateway {
  /** האם מותר לשלוח טקסט חופשי לאיש הקשר הזה כרגע.
   *  קריטי: לא מניח true. המימוש הרשמי מחזיר false מחוץ לחלון 24 השעות. */
  canSendFreeform(contactId: string): Promise<boolean>;

  sendMessage(input: {
    contactId: string;
    body: string;
    replyToId?: string;
    idempotencyKey: string;
  }): Promise<{ messageId: string; state: 'sent' | 'queued' | 'rejected' }>;

  /** קיים רק כדי שהמימוש הרשמי יוכל לממש אותו. במימוש הלא-רשמי — no-op. */
  sendTemplate?(input: {
    contactId: string; templateId: string; variables: Record<string, string>;
  }): Promise<{ messageId: string }>;

  /** מצב החיבור. מזין את ניטור הבריאות וזיהוי החסימה. */
  health(): Promise<{
    state: 'connected' | 'reconnecting' | 'qr_required' | 'throttled' | 'banned';
    since: string;
    detail?: string;
  }>;

  /** webhooks נכנסים מנורמלים לצורה אחת, ללא קשר לספק. */
  onInbound(handler: (msg: NormalizedInboundMessage) => Promise<void>): void;
}
```

> **`canSendFreeform` הוא הפרט שהופך את הכל להפיך.** אילו ההפשטה הייתה מניחה חופש מוחלט, המעבר ל-API הרשמי היה שכתוב של `comms.whatsapp`. עם הפונקציה הזו, זו החלפת מימוש.

## 3. שלושת המימושים

| | **GREEN-API** (נבחר) | **Baileys** self-hosted | **Cloud API** רשמי |
|---|---|---|---|
| פרוטוקול | WhatsApp Web (לא-רשמי) | WhatsApp Web (לא-רשמי) | רשמי של Meta |
| טקסט חופשי לכל אחד | ✅ | ✅ | ❌ תבניות מחוץ לחלון |
| תחזוקת פרוטוקול | **הספק סופג** | נופלת עלינו | Meta |
| הגנה מחסימה | **בנויה ומכוילת** | לבנות לבד | לא רלוונטי |
| תשתית | אין. HTTP | קונטיינר, סשן, reconnect | אין |
| עלות | חודשית לכל מספר | אפס שוטף | לכל הודעה/שיחה |
| נתיב הנתונים | **דרך שרתיהם** | הכל אצל הלקוח | דרך Meta |
| סיכון חסימה | קיים, מוקטן | קיים | אין |
| זמן לפיילוט | ימים (יש מסלול חינמי) | שבועות | שבועות (אימות) |

### הנבחר: GREEN-API

מקשרים את חשבון ה-WhatsApp Business הקיים בסריקת QR ומקבלים REST API + webhooks. הבוס ממשיך להשתמש בטלפון כרגיל, ואותו מספר משרת גם אותו וגם את המערכת — בדיוק כמו WhatsApp Web.

**ההכרעה היא שורת ההגנה מחסימה.** טבלת הנדסת הסיכון (סעיף 5) היא בדיוק מה ש-GREEN-API כבר בנו וכיילו על פני הרבה לקוחות. מימוש עצמי של אותה שכבה יהיה נחות ממנה למשך זמן ארוך.

### החלופה המתועדת: Baileys

מימוש TypeScript טהור של פרוטוקול WhatsApp Web הרב-מכשירי מעל WebSocket. כ-50MB לסשן.

**לא `whatsapp-web.js`:** הוא מריץ Chrome אמיתי דרך Puppeteer — כ-500MB לסשן, שביר, ונשבר בכל שינוי UI של WhatsApp Web.

מומלץ לעטוף ב-**WAHA** או **Evolution API** (שניהם self-hosted ב-Docker, חושפים HTTP + webhooks) כדי לקבל בידוד תהליכי במקום ספרייה מוטמעת בליבה.

**מתי לעבור אליו:** כשמספר הלקוחות הופך את העלות החודשית למשמעותית, או כשלקוח דורש שנתוניו לא יעברו בצד שלישי.

## 4. הסיכון — פעם אחת, במלואו

> זו **הפרה של תנאי השימוש של WhatsApp**. GREEN-API **מקטין את ההסתברות לחסימה אך אינו משנה את סוגה** — זה אותו פרוטוקול לא-רשמי, והשירות עצמו מציין זאת מפורשות.
>
> חשבונות נחסמים לצמיתות, בלי ערעור ובלי שחזור. מדווחות חסימות המוניות של משתמשי ממשקים לא-רשמיים.
>
> כאן מדובר ב**מספר העסקי של הבוס עצמו** — קו התקשורת העיקרי של העסק, על כל ההיסטוריה ואנשי הקשר שבו.
>
> **זו החלטה מודעת של בעל המוצר.** היא חייבת להיות מתועדת ומוסכמת מול כל לקוח שהמוצר מותקן אצלו — לא קבורה בהערת שוליים.

**שיקול נוסף שנוצר עם השירות המנוהל:** כל הודעה של כל לקוח עוברת בשרתי GREEN-API. זה מחייב DPA מולם, גילוי ללקוחות, ובדיקת מיקום השרתים — במיוחד בהינתן שכל הרעיון של התקנה נפרדת לכל עסק היה בידוד נתונים.

**נקודה מאזנת:** מה שמפעיל חסימות הוא בעיקר נפח גבוה למי-שאינו-איש-קשר, שיעור חסימות ודיווחים גבוה, וטקסט זהה בהמוניו. דפוס השימוש כאן — מענה לשיחות אמיתיות בנפח בינוני — רחוק מהפרופיל הזה. הסיכון אמיתי, אבל הוא לא גזירה.

## 5. הנדסת הסיכון — חלוקת האחריות

> **מה שמגן על המספר — של הספק. מה שאוכף את מדיניות העסק — שלנו.**
>
> אסור להישען על ספק חיצוני לאכיפת התקנון, גם כשהוא עושה עבודה טובה בשכבה שלו.

| מנגנון | אחראי | פירוט |
|---|---|---|
| קצב אנושי | **GREEN-API** | השהיות בין הודעות, מניעת רצף מהיר, חיווי הקלדה |
| עצירה בסימן סיכון | **GREEN-API** | השירות משהה שליחה בסימן ראשון לחסימה ומתריע למערכת |
| התמדת סשן ו-reconnect | **GREEN-API** | כולל זרימת QR מחדש כשהסשן נופל |
| תחזוקת פרוטוקול | **GREEN-API** | ספיגת שינויים מצד WhatsApp |
| **תקרות התקנון** | **אנחנו** | `maxOutboundPerHour/Day`, מרווח מינימלי, איסור טקסט זהה ליותר מ-N נמענים. **שכבה שנייה מעל שלהם** |
| **רק מי שכבר בקשר** | **אנחנו** | יזום מול מי שמעולם לא התכתב עם העסק דורש אישור מפורש. **החלטה עסקית, לא טכנית** |
| **בידוד והסגר** | **אנחנו** | הגשר מדבר עם הליבה רק דרך `WhatsAppGateway`. הודעות נכנסות עוברות `intake.triage` בדיוק כמו מייל |
| **ניטור וזיהוי חסימה** | **אנחנו** | קליטת ההתראות שלהם, מעקב `health()`, הסלמה מיידית לבוס |
| **failover** | **אנחנו** | נפילה אוטומטית למייל + נוהל מספר חלופי מתועד מראש |

## 6. השתלבות בארכיטקטורה

### הודעות נכנסות

```
GREEN-API webhook → channel-gateway
  → נרמול ל-NormalizedInboundMessage
  → דה-דופליקציה על messageId
  → חותמת מקור: זיהוי איש הקשר → boss | known_counterparty | unknown_external
  → InboundEvent → intake.triage  (הסגר: בלי כלי כתיבה)
  → ExtractedIntent[] → Orchestrator
```

**הגוף הגולמי לעולם לא מגיע ל-`comms.whatsapp`.** הוא מקבל את ה-intent המובנה בתוספת תמליל **מצוטט ותחום** שגם ה-system prompt וגם hook סריקת תוכן מתייחסים אליו כאל נתונים.

### הודעות יוצאות

```
comms.whatsapp מנסח
  → PreToolUse על wa.send_message:
      KillSwitch → תקרות התקנון → provenanceCeiling → BudgetGuard → RiskScorer
      + בדיקת doNotContact
      + בדיקת maxOutboundPerHour/Day
      + canSendFreeform(contactId)
  → allow | queue_approval | deny
```

### כערוץ אישורים

הגשר משמש גם למסירת כרטיסי אישור לבוס. **מענה בטקסט או במילת מפתח, לא בכפתורים** — כפתורים אינטראקטיביים אינם אמינים בלקוחות לא-רשמיים. הכרטיס מציג "השב 1 לאישור / 2 לדחייה / 3 לפרטים" ובנוסף קישור עמוק לדשבורד.

> **מסלול האישורים לעולם לא תלוי בגשר.** הדשבורד והמייל חייבים להיות עצמאיים באמת, כך שאם הגשר יורד המערכת ממשיכה לתפקד במלואה ורק ההתראה בנייד נעלמת. ראה [05-approvals.md](05-approvals.md).

## 7. הספייק — ראשון בתור לפני כתיבת קוד

ל-GREEN-API יש מסלול Developer חינמי שמספיק לבדיקה אמיתית, אז זה עולה זמן בלבד.

**לקשר מספר בדיקה — לא מספר עסקי אמיתי — ולהריץ שבועיים רצוף.** למדוד:

- יציבות החיבור ותדירות נפילות סשן
- אמינות ה-webhooks: האם הודעות הולכות לאיבוד? מה קורה כשהמערכת שלנו למטה?
- התנהגות ב-reconnect ובזרימת QR מחדש
- מה בדיוק עובר בהודעות מדיה, בהודעות קוליות ובקבוצות
- **מה קורה כשמנגנון ההגנה שלהם עוצר שליחה** — איך זה מדווח, ומה ה-`health()` מחזיר

זו ההנחה הכי שברירית בכל התכנון.

**שאלות מסחריות שיש לברר במקביל:** מיקום השרתים · DPA · מדיניות שמירת הודעות · תמחור לכל מספר בקנה מידה של עשרות לקוחות · **מה קורה למספר אם מפסיקים את המנוי**.
