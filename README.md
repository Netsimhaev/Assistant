# עוזרת אישית עסקית

עוזרת AI שמחליפה מזכירה/פקידת משרד, מותקנת בנפרד אצל כל עסק.
הארכיטקטורה המלאה: [docs/00-overview.md](docs/00-overview.md).

**מצב נוכחי: שלב 0 — עמוד השדרה של הממשל. בבנייה.**

---

## הרצה

```bash
npm install
cp .env.example .env      # התאם את DATABASE_URL אם צריך
npm run migrate           # יוצר את הסכמה
npm test                  # 98 מבחנים
```

דרישות: Node ≥ 22 · PostgreSQL (נבדק על 17.11) עם שני בסיסי נתונים — `assistant_dev` ו-`assistant_test`.

| פקודה | פעולה |
|---|---|
| `npm run migrate` | מריץ מיגרציות על `DATABASE_URL` |
| `npm run migrate:test` | מריץ מיגרציות על `TEST_DATABASE_URL` (דגל `--test-db`) |
| `npm test` | מריץ את כל המבחנים מול `TEST_DATABASE_URL` |
| `npm run typecheck` | `tsc --noEmit` |

## מה נבנה עד כה

השלד סביב **שער אחד** שכל קריאת כלי עוברת דרכו — `evaluateToolCall` ב-[src/policy/engine.ts](src/policy/engine.ts). תשע בדיקות, מהמוחלטת לזו שדורשת הכי הרבה עבודה:

```
kill switch → תקנון עדכני → הרשאת כלי → קריאה-בלבד? →
איסור מוחלט → doNotContact → אוטונומיה → תקציב → סיכון
                                          ⇓
                              allow | deny | queue_approval
```

| רכיב | קובץ | מה הוא מבטיח |
|---|---|---|
| מנוע המדיניות | `src/policy/engine.ts` | שער יחיד; **כוונה נרשמת לפני הקריאה**, כך שקריסה באמצע פעולה נראית |
| התקנון | `src/charter/` | חתימה מאמתת שינוי, קומפיילר ל-`PolicyBundle`, רינדור לעברית פשוטה שהבעלים חותם עליה |
| שכבת היכולות | `src/charter/capabilities.ts` | `ops.web` פשוט אין לו כלי מייל — אין לאן להזריק |
| ביקורת | `src/audit/log.ts` | שרשרת hash, append-only ב-DB, מזהה גם שינוי וגם מחיקה |
| Kill switch | `src/governance/killswitch.ts` | שלוש רמות, שורד restart כי המצב ב-Postgres |
| אישורים | `src/governance/approvals.ts` | לא חוסם ריצה; קושר ל-hash הקלט (TOCTOU) |
| סיכון | `src/policy/risk.ts` | שבעה ממדים, **המודל אינו במסלול** |
| תקציב | `src/policy/budget.ts` | סוכם את הפנקס במקום מונה שקריסה משאירה שגוי |

### תנאי היציאה של שלב 0

> דחיית מדיניות, אישור, ו-kill switch — כל שלושתם ניתנים להוכחה ממסלול הביקורת.

מוכח ב-[src/policy/engine.test.ts](src/policy/engine.test.ts). כמה תכונות שהמבחנים נועלים:

- מייל משולח לא מוכר **אינו יכול** להגיע ל-`auto_notify` גם כשזו ברירת המחדל — תקרת המקור גוברת
- אישור **נקשר ל-hash של הקלט שהוצג**; עריכה של הבוס קושרת מחדש לקלט הערוך
- `outbound` עוצר שליחה וממשיך לאפשר קריאה — עצירה חלקית היא הכוונה, לא פרצה
- `UPDATE` על `audit_log` נדחה ברמת ה-DB

## הערות למי שממשיך

**שכבת היכולות דוחה לפני התקנון.** אם `forbidden` בתקנון מכוון למחלקת פעולה שאף סוכן לא יכול להגיע אליה, החוק הוא קוד מת — השער יחזיר `tool_not_allowlisted` ולא `forbidden`. הבדיקה ב-`capabilities.test.ts` אוכפת שכל כלי מסווג הוא או בבעלות סוכן או ברשימת `UNOWNED_TOOLS` המפורשת.

**מחלקת פעולה חדשה = שתי עריכות.** להוסיף ל-`ActionClass`, ולמפות את הכלי ב-`src/policy/classify.ts`. כלי שאינו מסווג ואינו ב-`READ_ONLY_TOOLS` נכשל במבחן — בכוונה, כי אחרת הוא היה עובר את השער בשקט.

**כסף תמיד ביחידות מינור כמספר שלם.** `readAmountMinor` דוחה עשרוני במקום לעגל.

**`gov.risk` אינו מייצר את הציון.** הציון הוא קוד; הסוכן נועד לדעה שנייה מעליו. בשלב 0 הוא לא קיים בכלל, ומנוע החוקים עומד לבדו.
